# commit: 변경사항 분석 후 컨벤션 커밋

현재 작업 디렉토리의 git 변경사항을 분석해 논리적 단위로 나누고, 한국어 커밋 메시지를 만들어 **승인 절차 없이 바로** 커밋한다.

## 절차

### 1. 변경사항 분석

다음을 병렬로 실행한다.

- `git status` — 변경·추가·삭제된 파일과 untracked 파일 확인
- `git diff` — unstaged 변경 내용
- `git diff --staged` — 이미 staged된 변경 내용
- `git log -5 --oneline` — 최근 커밋 메시지 스타일 확인

git 저장소가 아니거나 변경사항이 없으면 그 사실만 알리고 종료한다.

커밋하면 안 되는 파일(`.env`, 키·토큰·자격 증명, `node_modules`, 빌드 산출물, 대용량 바이너리)이 변경 목록에 있으면 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류

변경 파일을 **하나의 목적**을 가진 단위로 묶는다.

- 기능 추가, 버그 수정, 리팩터링, 설정·의존성 변경은 서로 다른 커밋으로 분리한다.
- 같은 목적의 코드와 그 테스트는 한 커밋에 묶는다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 hunk를 쪼개지 않고 파일 단위로 가장 가까운 커밋에 넣는다. 이 사실은 완료 보고에 적는다.
- 변경이 하나의 목적뿐이면 커밋 하나로 충분하다. 억지로 쪼개지 않는다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>
```

- **type**: 아래 중 하나만 쓴다.
  - `feat` — 사용자에게 보이는 새 기능
  - `fix` — 버그 수정
  - `refactor` — 동작 변화 없는 구조 개선
  - `chore` — 설정, 의존성, 빌드, 문서 등 그 외
- **요약**: 한국어, 한 줄, 50자 안팎, 마침표 없음. 무엇을 했는지 능동형으로 쓴다. (예: `feat: 결과 창에 레트로 데스크톱 테마 적용`)
- **본문**: 요약만으로 이유가 전달되지 않을 때만 쓴다. "무엇"보다 "왜"를 적고, 줄은 72자 안팎에서 바꾼다.
- 1단계에서 확인한 최근 커밋 스타일과 어긋나지 않게 맞춘다.
- 시스템 안내에 커밋 attribution 줄(Co-Authored-By 등)이 주어져 있으면 메시지 맨 끝에 그대로 덧붙인다. 주어지지 않았다면 임의로 추가하지 않는다.

### 4. 커밋 실행

사용자 승인을 기다리지 않고 커밋 단위마다 순서대로 실행한다.

- 파일은 이름을 지정해 `git add <파일...>`로 staging한다. `git add -A`와 `git add .`는 쓰지 않는다.
- 메시지는 heredoc으로 전달해 줄바꿈이 깨지지 않게 한다.

### 5. 결과 보고

모든 커밋이 끝나면 `git status`와 `git log --oneline -n <커밋 수>`로 결과를 확인하고, 아래를 보고한다.

1. 커밋별 해시, 메시지, 포함 파일
2. 제외한 파일과 그 이유 (있을 때)
3. 한 파일에 섞인 변경을 합쳐서 커밋한 경우 그 내용

## 규칙

- `--no-verify`, `--amend`, `git push`, `git reset --hard`는 사용자가 명시적으로 요청하지 않는 한 쓰지 않는다.
- pre-commit hook이 실패하면 원인을 보고하고 고친 뒤 **새 커밋**을 만든다. hook을 우회하지 않는다.
- 커밋 메시지는 사용자가 읽는 말로 쓴다. 파일명 나열이나 "수정함", "변경" 같은 모호한 표현은 피한다.
