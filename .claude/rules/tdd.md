# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선한다.**
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 없거나 침묵하는 부분에만 적용한다.

## 적용 기준

### TDD 필수

- **비즈니스 로직**
- **API** (엔드포인트, 요청/응답 처리, 외부 호출 래퍼)
- **유틸리티/순수 함수**
- **버그 수정** (재현 테스트를 먼저 작성하고 실패를 확인한 뒤 수정)

### TDD 불필요

- 타입 정의 (`interface`, `type`)
- 설정 파일 (tsconfig, eslint, vite 설정 등)
- 순수 UI (로직 없는 마크업, 스타일링)
- SQL (스키마, 마이그레이션)

판단이 애매하면 **적용 대상으로 간주한다.**

## RED-GREEN-REFACTOR 사이클

### 1. RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 테스트 하나에 여러 동작을 섞지 않는다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류, import 실패, 오타로 인한 실패는 RED가 아니므로 테스트를 고친 뒤 다시 실행한다.

### 2. GREEN: 최소한의 코드로 통과

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI** — 아직 테스트가 요구하지 않는 기능, 옵션, 분기를 넣지 않는다.
- **신규 테스트와 기존 테스트 모두** 실행해 통과를 확인한다.

### 3. REFACTOR: 구조 개선

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지한다.** 리팩터 후 다시 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 RED에서 시작한다.

### 4. 반복

다음 동작이 남았다면 **RED로 돌아간다.** 한 사이클이 끝나기 전에 다음 동작을 구현하지 않는다.

## 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제하고 RED부터 다시 시작한다.**
- **"참고용"으로 남기는 것도 금지한다.** 주석 처리, 별도 파일 보관, 복사해 두기 모두 포함한다. 남아 있는 코드는 테스트 설계를 오염시킨다.

## 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트가 불필요하다" | 단순한 코드는 테스트도 단순하다. 비용이 거의 없는 테스트를 생략할 이유가 없고, 단순한 코드에서 나는 버그가 가장 늦게 발견된다. |
| "나중에 테스트를 추가하겠다" | 나중에 쓴 테스트는 구현을 그대로 따라 쓰게 되어 버그를 잡지 못하고, 대부분 쓰이지 않는다. 테스트 후행은 TDD가 아니다. |
| "시간이 없다" | 테스트 없는 코드는 디버깅과 회귀 수정으로 더 많은 시간을 쓴다. 급할수록 안전망이 필요하다. |
| "이미 짠 코드를 삭제하면 낭비다" | 이미 쓴 시간은 매몰 비용이다. 검증되지 않은 코드를 유지하는 비용이 재작성 비용보다 크다. 삭제 후 RED부터 다시 한다. |
| "프로토타입이다" | 프로토타입은 자주 그대로 프로덕션이 된다. 버릴 코드라면 어차피 적용 대상 밖이므로 이 규칙으로 판단하지 말고 사용자에게 먼저 확인한다. |
